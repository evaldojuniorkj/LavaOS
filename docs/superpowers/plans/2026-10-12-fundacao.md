# Fase 0 — Fundação: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** entregar a base local do LavaOS com banco, autenticação dos quatro perfis, isolamento por tenant, gestão mínima de membros, layout responsivo e verificações automatizadas.

**Architecture:** aplicação única Next.js App Router/TypeScript sobre PostgreSQL 16/Drizzle. Better Auth gerencia identidades e sessões, e suas organizações/membros são mapeados para as entidades do LavaOS; autorização de negócio é calculada no servidor. O login do lavador é um plugin local de PIN que emite sessões Better Auth, sem alterar a política de senha dos outros perfis.

**Tech Stack:** Next.js, TypeScript, Node.js, pnpm, PostgreSQL 16, Drizzle, Better Auth, Zod, Tailwind CSS, shadcn/ui, Vitest e Playwright.

**Spec:** [Especificação do MVP](../specs/2026-09-30-lavaos-mvp-design.md), §§2–4, 6–9. Ler também [a revisão técnica da Fundação](../reviews/2026-10-12-fundacao-spec-review.md).

**Estado:** aprovado pelo usuário em 2026-10-12. A primeira implementação foi descartada em 2026-10-27 (perdeu o vínculo git); este plano está sendo **re-executado do zero** na branch `fase-0-fundacao`, com subagent-driven-development e revisão por tarefa. Spec atualizada em 2026-10-27 (sem mudança na matriz de permissões nem no modelo da Fundação).

## Global Constraints

- “Next.js (App Router) + TypeScript”: aplicação única, servidor Node de longa duração.
- “PostgreSQL 16” e “Drizzle ORM”: migrations versionadas.
- “Better Auth”: o plugin de organizações representa o lava jato.
- “Tailwind CSS + shadcn/ui” e “pnpm”.
- “nenhuma consulta é feita sem esse filtro”: dados de domínio exigem `tenant_id`.
- “Quatro perfis fixos: `dono`, `gerente`, `recepcao`, `lavador`”.
- “toda server action e rota exige uma permissão explícita”; recusa “acesso negado”. Rotas públicas de login e protocolo auth são exceções declaradas, não operações de domínio.
- “O lavador nunca recebe valores em R$” nas telas, actions e eventos; na Fundação não há campos financeiros.
- “usuário + PIN numérico” de “4 a 6 dígitos”, criado pelo dono/gerente; sessão de “30 dias”; bloqueio após “5 tentativas erradas”.
- “membro desativado perde a sessão imediatamente”.
- “Interface e mensagens em português do Brasil”.
- “America/Sao_Paulo” para o dia operacional futuro; centavos inteiros e pontos-base para futuros cálculos.
- “Tabelas, campos, telas e regras de módulos futuros são introduzidos nas respectivas fases”.
- Fundação não inclui catálogo, clientes/veículos, OS, fila/SSE, PWA instalável, assistente, caixa, comissões, fidelidade, agenda, relatórios ou produção. Inclui somente equipe mínima para provar o acesso dos perfis. Não integrar TypeSafe nesta fase.
- Exceções de modelagem propostas: identidades/auth globais seguem contrato da biblioteca; `lava_jatos` é raiz do tenant. Demais tabelas próprias são locais ao tenant.

## Review Focus

1. Cookie legítimo com `tenant_id`/UUID de outro lava jato adulterado: negar sem revelar dados — tarefas 3, 6 e 8.
2. Membro desativado com tela aberta ou cookie antigo: próximo acesso já negado, inclusive endpoints auth protegidos — tarefas 4, 6 e 8.
3. Cinco PINs errados concorrentes/reinício do processo: bloqueio persistente e nenhuma tentativa extra autorizada — tarefa 5.
4. Reset concorrendo com login usando o PIN anterior: nenhuma sessão PIN antiga consegue passar pelo guard — tarefas 5 e 6.
5. Cadastro público ou rota nativa de organização usado para promoção de perfil: recusar, independentemente da UI — tarefas 4, 6 e 8.

### Modelo e contratos definidos pelo plano

- Organização do plugin → tabela `lava_jatos`; `id` é o tenant, `name → nome`, `slug` é chave técnica única, `telefone`/`endereco` opcionais no provisionamento local.
- Member do plugin → tabela `membros`; `organizationId → tenant_id`, `userId → user_id`, `role → perfil`, `createdAt → created_at`; adicionar `nome_exibicao`, `ativo` e `updated_at`. Um único perfil por vínculo; unique `(tenant_id, user_id)` e `(tenant_id, id)`.
- Tabelas core de usuário, conta, sessão, verificação, rate limit e eventual convite exigido pelo plugin: schema conforme versão fixada. Convite pode existir por contrato do plugin, mas seu fluxo HTTP fica bloqueado; sem implementar convites por e-mail. Mapear os quatro perfis para roles estáticos do plugin quando necessário, sem promover um `owner`/`admin` padrão a perfil local implicitamente. Bootstrap e criação de membros persistem explicitamente o perfil validado.
- `credenciais_lavador`: UUID, tenant, membro, `usuario_normalizado`, hash de PIN, `versao` inteira positiva, erros consecutivos, bloqueado até, timestamps; unique `(tenant_id, usuario_normalizado)` e `(tenant_id, membro_id)`. FK composta para membros; credenciais não são campos públicos do user/member.
- Sessão PIN tem campos técnicos server-only `pinMemberId` e `pinCredentialVersion`; guard compara a versão atual. O usuário auth técnico do lavador pode ter e-mail interno `${userId}@lavador.invalid`, jamais usado para login, entrega ou recuperação; não possui conta de senha de e-mail.
- Sem tabela auth paralela para sessão e sem autorização derivada do `perfil` recebido do cliente. Mapeamentos de colunas e IDs serão verificados pelos tipos do adapter e por integração real.

**Propostas de parâmetros:** PIN bloqueado por 15 minutos; lavador 30 dias absolutos, demais 7 dias absolutos; usuário normalizado com trim/lowercase, 3–30 caracteres `[a-z0-9_.]`; `LAVAOS_PILOT_SLUG` define o tenant para o login público do piloto. Senha de staff mínimo 8 caracteres; limite de máximo conforme política da versão Better Auth, validado na entrada. Esses parâmetros complementam a spec e foram aprovados pelo usuário junto com o plano em 2026-10-12.

### Interfaces locais

Assinaturas são contratos **propostos para o LavaOS**, não APIs já existentes nem assinaturas inventadas de biblioteca. Ajustes necessários em tipos externos devem ficar no adapter auth, preservando estes contratos.

| Arquivo | Interface produzida |
|---|---|
| `src/lib/env.ts` | `parseServerEnv(input: Record<string, string | undefined>): ServerEnv` |
| `src/lib/db/client.ts` | `createDatabase(url: string): { db: Database; close(): Promise<void> }`; singleton `getDatabase(): Database` |
| `src/lib/auth/types.ts` | `Perfil`; `Permissao` com as entradas exatas da spec §3; `TenantScope { readonly tenantId: string }`; `TenantContext` acrescenta `userId`, `memberId`, `perfil`, `sessionId` e marca interna emitida somente pelo guard |
| `src/lib/auth/permissions.ts` | `can(perfil: Perfil, permissao: Permissao): boolean`; `assertPermission(ctx: TenantContext, permissao: Permissao): void` |
| `src/lib/auth/context.ts` | `requireTenantContext(headers: Headers): Promise<TenantContext>`; `requirePermission(headers: Headers, permissao: Permissao): Promise<TenantContext>` |
| `src/lib/auth/route-policy.ts` | `isAuthHttpPathAllowed(method: string, path: string): boolean` |
| `src/lib/auth/credentials.ts` | `hashSecret(secret: string): Promise<string>`; `verifySecret(secret: string, hash: string): Promise<boolean>`; wrappers do hasher configurado no Better Auth, sem algoritmo próprio |
| `src/lib/auth/pin.rules.ts` | `isValidPin(pin: string): boolean`; `normalizeUsername(value: string): string`; `isPinBlocked(blockedUntil: Date | null, now: Date): boolean`; `nextPinFailure(failed: number, now: Date): { failed: number; blockedUntil: Date | null }` |
| `src/lib/auth/pin.repo.ts` | `resolvePilotScope(slug: string): Promise<TenantScope>`; `findCredential(scope: TenantScope, usuario: string): Promise<PinCredential | null>`; `verifyAttempt(scope: TenantScope, usuario: string, pin: string, now: Date, hasher: PinHasher): Promise<PinAttempt>` |
| `src/lib/auth/pin.plugin.ts` | `lavadorPinPlugin(): BetterAuthPlugin`; endpoint `POST /api/auth/lavador-pin/sign-in` com `{ usuario, pin }` |
| `src/modules/equipe/equipe.repo.ts` | `listMembers(ctx: TenantContext): Promise<MemberSummary[]>`; `findMember(ctx: TenantContext, memberId: string): Promise<MemberSummary | null>` |
| `src/modules/equipe/equipe.service.ts` | `createMember(ctx: TenantContext, input: CreateMemberInput): Promise<MemberSummary>`; `deactivateMember(ctx: TenantContext, memberId: string): Promise<void>`; `resetPin(ctx: TenantContext, memberId: string, pin: string): Promise<void>` |
| `src/modules/equipe/equipe.actions.ts` | `createMemberAction(input: unknown)`; `deactivateMemberAction(input: unknown)`; `resetPinAction(input: unknown)` retornam `Promise<ActionResult<MemberSummary | null>>` |

Tipos complementares: `Database` é o cliente Drizzle configurado, `ServerEnv` contém URLs/segredos validados; `MemberSummary { id, nomeExibicao, perfil, ativo }` nunca inclui hash/contadores. `PinCredential` é privado ao servidor, com membro, hash, versão e estado de bloqueio. `PinHasher` fornece `hash(secret)` e `verify(secret, hash)`, ambos assíncronos, usando o hasher de Better Auth. `PinAttempt` é união `{ ok: true; userId; memberId; credentialVersion } | { ok: false; code: 'INVALID_CREDENTIALS' | 'PIN_BLOCKED'; retryAfterSeconds?: number }`.

`CreateMemberInput` é união: staff `{ perfil: 'dono' | 'gerente' | 'recepcao'; nomeExibicao; email; senha }` ou lavador `{ perfil: 'lavador'; nomeExibicao; usuario; pin }`. Todos os campos textuais são strings. `ActionResult<T>` é `{ ok: true; data: T } | { ok: false; code: string; message: string; fieldErrors?: Record<string, string[]> }` sem detalhes internos.
